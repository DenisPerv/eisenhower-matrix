# TasksDashboard

Eisenhower matrix task app, UI 4-5 "Aurora instrument", on a Supabase database (TasksDashboardDB). `TasksDashboard.html` plus `config/tasksdashboard.config.js`: no server, no build, no dependencies. The page opens from `file://` (or a static host, see Hosting) and talks only to the Supabase project in its config. A small CLI in `cli/` reads and writes the same database.

The household's own setup lives in HomeOS (`references/homeos/tasksdb/`); this README is enough to set the app up for another household.

**Documentation:** `docs/README.md` is the index: architecture, database, sign-in, hosting, testing and release, the read API (`docs/api/`: `openapi.yaml` and curl examples for the weekly review report), access requests and the deployment runbook. This README stays the technical reference.

## Set up (Phase 0, once)

1. **Supabase project.** supabase.com → New project (free plan). Note the project URL (`https://<ref>.supabase.co`).
2. **Auth settings.** Authentication → Sign In / Providers: turn off "Allow new users to sign up", "Allow manual linking" and "Allow anonymous sign-ins"; Email provider on, "Confirm email" off.
3. **Logins.** Authentication → Users → Add user → Create new user, one per person and per agent (email + password, "Auto Confirm User" on). The seed expects four: two people (`maksym`, `anastasiia` in `004_seed.sql`; change the handles for your household) and two agents (`homeos-agent`, `telegram-bot`).
4. **Data API.** Project Settings → Data API: `public` exposed, "Automatically expose new tables" off. Never click a table in the Data API page: it would replace the explicit grants with defaults that include `anon` (if it happens, re-run `003_rls.sql`).

## CLI

- **Common options:** `--env <file>` (KEY=value lines; `TASKSDB_*` variables from the environment fill gaps), `--as <handle>` (default `homeos-agent`; reads `TASKSDB_<HANDLE>_EMAIL` / `_PASSWORD`, with `AGENT` and `TELEGRAM` for the two agents), `--for <handle>` (`on_behalf_of`, a person), `--via <channel>` (`created_via` and `x-homeos-via`, default `script:tasks-cli`), `--run-id`, `--json`, `--dry-run` (reads, sends no write).
- **Tasks:** `<ref>` is `LIST#num` (`backlog#12`, `maksym/backlog#12`), a live task by its list and number.
- **Target** (`show`, `update`, `done`, `reopen`, `cancel`): `<ref>`, `--key <dedup_key>`, or title words with exactly one match (`--in <list>` narrows; the `find` rules). No match: exit 1. Several matches: they are listed (`--json`: `{ "candidates": [...] }`), exit 10, nothing is written; name one with its `<ref>`. Changes are for tasks and reminders only (another category: exit 1, nothing written).
- **Sensitive data:** `update` screens the new title, body and tag names with `sensitiveCheck`, the same rules as `assert_no_sensitive` (`db/002`: card numbers with a Luhn check, IBANs, ID numbers; links ignored): exit 5 and nothing is sent. The database trigger is the second line for every command.
- **When:** `YYYY-MM-DD` (09:00) or `YYYY-MM-DD HH:mm` in Europe/Lisbon, or ISO with an offset.
- **Env:** `TASKSDB_URL`, `TASKSDB_ANON_KEY` (the publishable key), and the login pairs. The URL and key get the page's config checks (https or localhost, never a secret key); a failure is exit 2.
- **List status:** every write reads its list first; an archived list is exit 8 and nothing is sent. `overdue` and `do` skip archived lists.
- **Output:** one line per item, `<initial><num> · title · due · list` (`find`, `show`, `update`, `done`, `reopen`, `cancel`: `<ref> · category · status · title · due · quadrant`, the `<ref>` usable as the next target), or `--json`.
- **Exit codes** (`EXIT`): 0 ok, 1 error (including not allowed and a bad value, 22023 without "sensitive data"), 2 env missing, 3 conflict, 4 duplicate, 5 sensitive data, 6 unreachable, 7 auth failed, 8 list archived (or, for `restore-list`, not archived or not found), 9 a limit (54000, see Limits), 10 several matches (listed, nothing written).
- It never prints an env value, a token or a password.

## Limits

- Local (`file://`), or hosted: see `docs/deployment/` and, in HomeOS, `references/homeos/tasksdb/hosting-plan.md`. The household copy is on Cloudflare Pages. Supabase's free plan cannot serve the page as HTML.
- `file://` storage is shared by every local page in the same browser profile: they can read `td.auth` (a refresh token), `td.accounts` (email addresses) and the `td.auth` BroadcastChannel (new token pairs). Open only files you trust in that browser profile; sign out on a shared computer. A hosted copy's storage is readable only by its own origin.
- Tags round, until the release: the hosted page (old code) rewrites the preferences row without `tagListFavs` and `tagListOrderV` and may set the landing list through its old ★ (`set_default_tag_list`); an old client open on any device does the same. The next load of this version migrates the row again (a stored order that holds my lists is kept) and `tagListFavs` falls back to the landing list.
- On the free plan a session never times out; Sign out (or revoking sessions in the dashboard) ends it.
- No trash view: a deleted item is recoverable only by admin SQL after the 8 s Undo.
- No password sign-in, sign-up or reset in any client (Google only, 2026-10-30); new accounts come only through Google (when sign-ups are on, behind the sign-up hook). `file://` cannot sign in (Google needs an https or localhost origin); open the page on localhost or the app host.
- No unblock in the app: "Decline and block" is undone by deleting one's own `invite_blocks` row (REST) or by admin SQL.
- **Limits** (`ops.settings`, `db/009`; admin SQL tunes them). Over one: 54000 in plain words, CLI exit 9.

  | Who | Limit |
  |---|---|
  | guests | 20 live lists (100 with archived), 1,000 live items they created (3,000 with deleted), 500 live tags, 10 live tag lists (50 with archived, `db/012`), `body_md` ≤ 10,000 characters, `details` ≤ 8 KB, 2,000 item writes a day, 120 item writes a minute |
  | household | 50 live lists each, 5,000 live items per list, 5,000 live tags, 30 live tag lists each (`db/012`), 1,000 item writes a minute (people and agents) |

A list under `+N` that should be on a panel: the window is too narrow (the Lists window says so). "Last backup time unknown": no backup run has recorded its time yet (`ops.settings`, `db/029`). Nothing records a deleted list |

- **KPI:** an item counts in the list it is in now (events are readable through the item's current list), so a moved item's history follows it; the quadrant of the past is derived with today's urgency settings; history starts at the audit trigger (`db/002`), before it items show as they are now. Without `db/013` the history comes in REST pages, four at a time: about 0.6-0.7 s for each 4,000 events (measured 2026-10-28), so about 12,000 events fit in 2 s.

- No repeat, subtasks, effort, reminders delivery or `.ics` export in the app.
- The End field uses the browser's date-time control, so its format follows the system locale.
