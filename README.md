# TasksDashboard

Eisenhower matrix task app, UI 4-5 "Aurora instrument", on a Supabase database (TasksDashboardDB). `TasksDashboard.html` plus `config/tasksdashboard.config.js`: no server, no build, no dependencies. The page opens from `file://` (or a static host, see Hosting) and talks only to the Supabase project in its config. A small CLI in `cli/` reads and writes the same database.

The household's own setup lives in HomeOS (`references/homeos/tasksdb/`); this README is enough to set the app up for another household.

**Documentation:** `docs/README.md` is the index: architecture, database, sign-in, hosting, testing and release, the read API (`docs/api/`: `openapi.yaml` and curl examples for the weekly review report), access requests and the deployment runbook. This README stays the technical reference.

## Set up (Phase 0, once)

1. **Supabase project.** supabase.com → New project (free plan). Note the project URL (`https://<ref>.supabase.co`).
2. **Auth settings.** Authentication → Sign In / Providers: turn off "Allow new users to sign up", "Allow manual linking" and "Allow anonymous sign-ins"; Email provider on, "Confirm email" off.
3. **Logins.** Authentication → Users → Add user → Create new user, one per person and per agent (email + password, "Auto Confirm User" on). The seed expects four: two people (`maksym`, `anastasiia` in `004_seed.sql`; change the handles for your household) and two agents (`homeos-agent`, `telegram-bot`).
4. **Data API.** Project Settings → Data API: `public` exposed, "Automatically expose new tables" off. Never click a table in the Data API page: it would replace the explicit grants with defaults that include `anon` (if it happens, re-run `003_rls.sql`).

## Config

```js
window.TD_CONFIG = {
  supabaseUrl: 'https://<ref>.supabase.co',
  publishableKey: 'sb_publishable_…',
  pollMs: 30000,
};
```

- Public values only; the lock is RLS plus closed sign-ups.
- A missing file, a URL that is not https (or `http://localhost`), an empty key, a secret key, or `pollMs` outside 5000-600000 shows "The page is not set up yet." with the errors.
- The config is a `.js` file because a `file://` page can load a script beside it but cannot read a `.json` file.

## Open and sign in

Double-click `TasksDashboard.html` (Chrome or Edge on Windows 11 for the intended fonts: Segoe UI Variable, Bahnschrift, Sitka, Cascadia Mono).

| Situation | What shows |
|---|---|
| no saved session, hosted page (https, or `http://localhost`) | "Continue with Google", "Stay signed in on this computer" (ticked), "Other ways to sign in" (the password form; open when an email is prefilled or the last account on this browser used a password), the privacy line |
| no saved session, `file://` | the password form (Email, Password, Stay signed in), a note that Google works on the hosted page, the privacy line |
| saved session | the board, after a silent token refresh |
| back from Google (`?code=`) | the code is swapped at once, then removed from the address; the board |
| back from Google with an error | the sign-in screen with the reason in plain words (`oauthMessage`) |
| the database can't be reached | "Can't reach the database." with Retry (a free project pauses after a week without use; restore it in the dashboard) |
| a login without a profile row | "This login can't open the board." with Sign out |
| `?profile=<handle>` | only prefills the form's email, when this browser has seen that account sign in |

- **Continue with Google** (PKCE, no library): a verifier from 48 random bytes in `sessionStorage` `td.pkce` (with the Stay signed in choice), then `GET /auth/v1/authorize?provider=google&redirect_to=<origin + path>&code_challenge=<S256>&code_challenge_method=s256` (`authorizeUrl`; `login_hint` and `prompt=select_account` when picking a remembered account). Back with `?code=`: `POST /auth/v1/token?grant_type=pkce` with `{ auth_code, code_verifier }`, `history.replaceState` drops the code (`readCallback` keeps other parameters, drops any token in a hash), `td.pkce` is deleted. The session then works as a password one. Supabase needs the page origin in Authentication → URL Configuration (Site URL, Redirect URLs) and the Google provider on.
- **Refusals in plain words** (`oauthMessage`): "Sign-up is by Google only.", "TasksDashboard is full right now. Try again later." (the sign-up hook, `db/010`), "New accounts are not open yet. Ask Maksym." (sign-ups off), "Google sign-in was cancelled.", "The Google sign-in expired. Try again." (no or a stale `td.pkce`), "This login signs in with a password only." (agents).
- **Privacy line** (`PRIVACY`): "We store your email, name and the items you create. Only people you share a list with see them. Ask Maksym to delete your account."
- **Privacy page** `privacy.html`: a static page (no script) with the same promise in more detail: what Google sign-in shares (email, name, picture), who sees what, where it is stored (Supabase, Cloudflare Pages), how to ask for deletion. It is the privacy policy link of the Google consent screen and is deployed at `/privacy.html`.
- **Access request page** `request.html` (published at `/request`; access-backup-plan A1): a stranger who is not let into the hosted board asks for access there. It loads no board data and has one inline script and the config. Continue with Google runs the same PKCE flow as the board (`redirect_to` = `<origin>/request`, `prompt=select_account`, verifier in `td.request.pkce`), then `rpc/my_access_request`; only when it returns no row (or a `removed` one) `rpc/request_access` and `rpc/my_access_request` again (`db/015`), so a reload writes nothing. A row, a one-row array or nothing are all read.

  | `data-state` of `#app` | When | Shows |
  |---|---|---|
  | `signedout` | no session in this tab | "Ask for access", Continue with Google (off on `file://`, with "Open this page on its https address to sign in."), what is kept (email, name, time) |
  | `sending` | an RPC is on its way | a scan line |
  | `sent` | status `pending` | the coffee break (inline SVG; the steam stops moving with reduced motion), "Your request is sent. We'll let you in soon.", Requested (local `yyyy-mm-dd HH:MM`), Account, Status |
  | `approved` | status `approved`, or `request_access` refuses a household member (`22023` "already have access") | "You're in", the approval time, Open TasksDashboard (`/`) |
  | `declined` | status `declined` | "Request declined", the decision time |
  | `cap` | `54000` from `request_access`, or the sign-up hook's "full right now" | "Try again later" |
  | `error` | any other failure, no network, 429 | the reason and Try again |

  Back from Google with an error: the board's plain words (cancelled, expired). A 401 refreshes once, then signed out with "Session ended. Sign in again.". Use another account: `/auth/v1/logout?scope=local` and the tab forgets the session. The look is the board's Aurora instrument tokens; `td.theme` is honoured.
- **Sign in with a password:** Enter submits. A wrong password shows "Email or password is wrong."; 429 shows "Too many attempts. Wait a minute, then try again." The message takes focus. No automatic retry, no sign-up, no password reset (password logins are made in the Supabase dashboard: the household, its agents, tests).
- **Stay signed in:** ticked keeps the refresh token in `localStorage` `td.auth`; unticked keeps it in `sessionStorage` (this tab only; a new tab asks again). The access token stays in memory. `td.auth` also holds the login's id: a tab reads its own `sessionStorage` first and never takes another person's token.
- **Several tabs:** a refresh runs under the Web Lock `td.refresh`, and the BroadcastChannel `td.auth` hands the new token pair to the person's other tabs (refresh tokens rotate; reusing an old one ends the session). Parallel 401s cause one refresh, not one each.
- **401:** one silent refresh and a retry; if that fails, the form shows "Session ended. Sign in again." and the waiting changes are sent after the next sign-in.
- **Account menu (the name; a badge counts open invitations):** the display name and the session email; Tags; Sharing; General settings (people); Urgency settings; Timeline (draft) (opens the Timeline view), Card layout, Archived lists, Hidden lists (when any); Sign out (`/auth/v1/logout?scope=local` with a fresh token: this browser only; other devices stay signed in; with changes still waiting it sends them first, and if they can't be sent it says so and signs out on the second click). Nothing from other people's profiles is listed, and no token of another account is kept. Round 4 removed **Accounts on this browser** (switch, forget) and **Add account**: to use another account, Sign out and sign in again.

## Model

| Quadrant | Row | Column | Title | Colour |
|---|---|---|---|---|
| A | important | urgent | Do | red |
| B | important | not urgent | Plan | green |
| C | not important | urgent | Delegate | yellow |
| D | not important | not urgent | Eliminate | grey |

- Grid order: B Plan, A Do on top; D Eliminate, C Delegate below.
- **Quadrant:** `items.quadrant`. An item without one (from the CLI without `--q` or another project) is shown where `deriveQuadrant` puts it, and nothing is written back: important = `priority` ≥ 3 or category `reminder`, `tbd` or `decision`; urgent = the pin (`urgent_pin`), else the deadline inside the urgency window (Settings).
- **Card number:** `<first letter of the list><num>`; `num` is set by the database per list (a moved item takes the next number of its new list).
- **Now** is recomputed on every render and poll. Dates show and are entered in the browser's time zone and are stored as `timestamptz`.
- **Statuses:** `done` and `cancelled` go to the Archive (cancelled with a mark). `inbox`, `in_progress`, `waiting`, `proposed`, `agreed` show as a small badge. Restore puts back the status from before completion (from `item_events`), `open` if unknown.
- **Badges on a card:** "check" (an assistant added it with low confidence: `review_state = needs_review`; the tooltip gives `ai_confidence`), the status, the category (except `task`).

## Data and sync

- **Load:** lists (`archived_at=is.null`), my `list_members` rows (role, `hidden_at`), categories, profiles (my own row; the household's rows for household members, by RLS; `email` is not readable), `rpc/visible_profiles` (names of people I share a list or tag list with), my tag lists (with `archived_at`) and `tag_list_members` rows, live tags (`select=*`: when the rows carry `updated_at`, `db/012`, the poll also reads changed tags), `rpc/my_invitations`, my open notes of a first share (`shared_notices?seen_at=is.null`), my preferences, then every live item and every live `item_tags` row. Every load pages with `order=id&limit=1000&offset=…` (`item_tags`: `order=item_id,tag_id`) until a short page.
- **Tags** (`item_tags`, `db/009`): a task holds tag ids; a chip shows the tag's name, with the owner's initial when two people's tag lists hold the same name (`tagLabels`; never on my own). Tags of a hidden or an archived tag list don't show. Adding writes `item_tags` (a removed row is revived by PATCH `removed_at=null`, else inserted); removing sets `removed_at`. These go after the item's own fields in the same queue, without a version (the last write wins). A new name is created on Save in the tag list it was typed in (`ensureTags`; at the end of its `tags.sort`; a deleted one with that name is revived). Renaming a tag is one PATCH on `tags`; deleting sets `tags.deleted_at` and takes it off every item I may edit. The legacy `items.tags` column is never read or written by the page.
- **Tag lists** (`db/012`): several per person; exactly one is my default (★, where tags from HomeOS, the bot and the CLI go). What I may do on one follows my role there (`tagListRights`):

  | Role | May |
  |---|---|
  | viewer | put its tags on items I may edit |
  | contributor | also add, rename and reorder its tags |
  | editor | also delete its tags, rename the list, delete (archive) it, move its tags to another list of the same owner, share it (up to editor) |
  | owner | also make it the default, reorder the lists, change roles, remove people |

  An archived tag list is read only for everyone (no new tags, uses or renames) until an owner or editor restores it; the default is never archived. Writes: `rpc/create_tag_list`, `rpc/set_default_tag_list`, `rpc/set_tag_list_archived`, `rpc/move_tags` (a name the target already holds is merged into it), PATCH `tag_lists` (`name`, `sort`) and `tags` (`name`, `sort`).
- **Owner:** a new item from the page carries `owner_id` = me (who it is for; "Mine"). Cards and the task window name people by display name ("(you)" for me).
- **Roles** (`list_members.role`): viewer reads only; contributor adds and edits only items they created, never deletes; owner and editor do everything. The page hides what the role can't do; the database enforces it.
- **Saving:** every change is shown at once and queued: one serial queue per item, changes to the same item merged. Each PATCH carries `version=eq.<the version the last response returned>` and `x-homeos-via: app`. A new item is sent with a client `crypto.randomUUID()` as `id`; a retry that gets 409 / 23505 counts as saved.
- **Conflicts (0 rows updated):** the page reads the item. Someone else saved first and changed other fields: mine are re-applied on the new version. They changed the same field: their version stays, and an edit from the task window reopens it with my text and a note saying what changed. The same version: "You can't edit this item here", and the item goes back.
- **Task window:** Save sends only the fields changed in the window. If the item changed while the window was open (a poll updates it in place) and someone else changed one of those same fields, the window reopens with the person's text and a note instead of overwriting it.
- **Links** (`db/018`): `item_links` rows of kinds `depends_on` (from comes after to, its predecessor) and `parent` (from is a child of to), read with `removed_at=is.null` on load and polled by `changed_at` (`linkPollFilter`, the same 120 s overlap) with removed rows; a link shows only when both ends are loaded (`linkIndex`). Changes go through `rpc/link_items` and `rpc/unlink_items` in one serial queue (`LQ`, after the item's own insert for a new task); a refusal puts the link back and says why (`DB_TEXT`: a loop, a second parent, a deleted task, too many links). On a database without 018 the load answers 400 and the links UI is not drawn (`LINKS_READY`).
- **Errors** (`restError`): 22023 starting "sensitive data" the database's text (card, IBAN or ID number; the window stays open); any other 22023 a bad value in plain words (`DB_TEXT`, e.g. "The person it is for is not a member of this list."; kind `invalid`, the window stays open), or "This list is archived. Restore it first."; 54000 a limit (`DB_TEXT`, e.g. "This list is full: its item limit is reached."); 42501 / 403 "Not allowed for your role on this list.", "This list is archived. Restore it first." or a sharing text from `DB_TEXT` ("This invitation is no longer open.", "Owners can't leave their own list.", …); 23514 "The title is over 300 characters."; 23505 on a list "A list with this name exists.", on a tag list "You already have a tag list with this name."; the database's own text from `DB_TEXT` is used before the "archived" fallback (so "the default tag list is not archived" reads "The default tag list can't be deleted. …"), and an archived tag list reads "This tag list is archived. Restore it first."; 401 refresh once; 429 wait.
- **Offline:** a network error, a 5xx or a 429 keeps the change in the queue ("Offline: N changes waiting", or "The database is busy" for 429); it is sent on `online`, on the next poll or on focus. Leaving the page with changes waiting asks first.
- **Poll:** every `pollMs` while the page is visible, and on focus: first my open notes of a first share (`shared_notices?seen_at=is.null`; on focus they come with the lists; a note on a list or tag list the page does not know reloads lists, tag lists and tags, once per note (`NOTICE_TRIED`); a note whose target is still unknown after that, because it was revoked, removed or archived before it was seen, is not shown), then items with `updated_at` ≥ the newest seen minus 120 s (`POLL_OVERLAP_MS`), deleted ones included; versions dedupe; items with waiting changes are skipped. Then `item_tags` with `changed_at` ≥ the newest seen minus 120 s (`tagPollFilter`), soft removals included (`mergeTagRows`; an unknown tag id is noted even on an item with changes waiting, whose row is still skipped). Unknown tag ids, from any poll, are read with `tags?id=in.(…)`; then, from `db/012` on, tags with `updated_at` ≥ the newest seen minus 120 s (`tagDefsFilter`, deleted ones included) are merged (`mergeTagDefs`: a rename relabels the chips, a deleted tag goes). Before `db/012` that request is never sent (detected from the loaded rows, so nothing fails). A tag on a tag list the page does not know reloads lists and tag lists. On focus, or when an item shows up on an unknown list or a tag on an unknown tag, lists, roles, categories, tag lists, tags and invitations load again; a list or tag list that became readable reloads every live `item_tags` row.
- **Hidden lists:** "Hide for me" (`rpc/set_list_hidden`) takes a list off my chips, All and search; Account menu → Hidden lists → Show again.
- **Card order:** the shared `items.sort_key` (`db/005`), ascending; cards without one go last. A dropped card takes the midpoint of its new neighbours (±1024 at the ends); a quadrant with missing keys or a gap under 1e-6 is renumbered with spacing 1024 first. New cards go on top.
- **Undo** (toast, 8 s, or Ctrl/Cmd+Z): sends the inverse as a new versioned write: add → soft delete (no Undo where the role can't delete), delete → restore, done / cancel → the earlier status, move or edit → the old fields.
- **Delete** is a soft delete (`deleted_at`). There is no trash view: after the 8 s Undo, only admin SQL brings an item back.
- **Archived lists:** an owner archives a list from its `…` chip menu (with a question). It leaves the chips, All and search; its items are never shown or edited, and the database refuses any update of them (`db/006`). Archived lists (menu) shows each with Restore for owners.
- **New list:** `rpc/create_list_row` (`db/012`; `p_name`, `p_shared`), private. Household members also see "Share with the household and the HomeOS agent" (ticked; `p_shared`, which adds the other household people and `homeos-agent` as editors). The database makes the slug (the name's ASCII letters and digits, else `list-<6 hex>`, `-2`, `-3` … on a clash with any of my lists) and returns the row.
  - Enter in the name (or on the check box) is Create, not Cancel (P1 fix F1: the form's first button is Cancel).
  - Create is disabled while it runs. The answer (`{ id, slug, name, sort, … }`, or a uuid from an older database: `createdList`) is put into the page at once and selected; nothing is reloaded (an empty list has no items or tags; the next poll reconciles). The page marks `td:list-rpc` and `td:list-shown` (`performance.mark`).
  - My archived lists are read when the window opens. A name I already use (case and outer spaces ignored, `listNameClash`): "You already have a list named X." and nothing is sent; an archived one offers **Restore it** or **Create "X (2)"** (`freeListName`). Names repeat freely across people.
  - A 23505 the page did not foresee (another tab made the list): it reads my lists again and names the clash.
- **Sharing** (`db/010`, `db/012`):
  - **Share** (list chip menu → Share…, Account menu → Sharing → My lists, Account menu → Tags → Share on a tray; owners of a list, owners and editors of a tag list, `canShare`): the people on it (`rpc/list_people` / `rpc/tag_list_people`: members; the owner gets a role select and Remove; invitations as "pending" with Revoke via `rpc/revoke_invite`, which refuses an editor's revoke of someone else's invitation), and Email + Role → `rpc/share_list` / `rpc/share_tag_list` with `p_join: true`. The people are read again on open, after each action, on window focus and every `SHARE_REFRESH_MS` (10 s) while the window is open (P1 fix F2: someone who leaves meanwhile drops off); a quiet read redraws only when the people changed and never under an open role menu. Roles: Editor, Contributor, Viewer for both. No email is sent. The first share to a person who has an account joins them at once (`db/012`: no earlier invitation for that target, no block); anyone else gets an invitation to accept. The answer is `{ ok: true }` either way.
  - **Note of a first share** (`shared_notices`): "X shared the list “Y” with you as Editor." (`noticeText`), pinned at the bottom right (not a dialog, so the board keeps updating), one per open note: **Keep** (`rpc/answer_shared_notice` `seen`), **Leave** (`leave`), **Block** after a question (`block`: leaves everything that person joined me to without Accept, blocks them, marks their notes seen).
  - **Account menu → Sharing:** Invitations (`rpc/my_invitations`: Accept → `rpc/accept_invite`; Decline; Decline and block, after a question → `rpc/decline_invite`), My lists (Share), Shared with me (role and owner; People, Hide for me or Show, Leave → `rpc/leave_list` after a question).
  - **List chip menu:** owner: Share…, Archive; member: People (the same window read only: who is on it, no share form), Hide for me, Leave; both: Archived lists, Hidden lists. Round 4: an owner has no separate People entry, since Share already lists the people (`membershipActions`).
  - **Account menu → Tags:** every tag list I can see, stacked as trays in the task window's order (`tagGroups`: my default first with ★, my other lists by `sort`, then shared lists in my order, `tagListOrder`, else by owner name), each with its tags by `tags.sort`, then name. Per tray, as my role allows: ☆ makes it the default; the name is a text box (rename); Share; **Delete list** after a question (archives it: its chips leave every card); + adds a tag; for shared trays the owner and my role, Hide for me or Show (`rpc/set_tag_list_hidden`), Leave (`rpc/leave_tag_list`). A tag opens its menu on click or right-click: Rename (also F2), **Move to list** (`moveTargets`), Count as Mine / Don't count as Mine (`profiles.mine_tag_ids`, at most 50; a "Mine" tag has an accent underline), Delete. Drag a tag onto another tray to move it, or between tags of its tray to reorder it (a midpoint `tags.sort`, Alt+Left / Alt+Right); drag my trays by their grip to reorder them (`tag_lists.sort` 1, 2, 3 …, Alt+Up / Alt+Down on the name). New tag list + Create list (`rpc/create_tag_list`). **Archived tags** shows the archived tag lists the same way, read only, with Restore (owners and editors).
- **General settings → Welcome note → Show again** shows the first-login welcome once more.
- **General settings → Display name and Time zone** (people): PATCH of my own `profiles` row (`display_name`, `timezone`; the time zone from the browser's list, the browser's own by default).
- **Sources:** the task window lists the item's `item_refs` (read only; links are shown as text). Round 4: only when Card layout → Source is on and the board shows All lists (`showSource`); otherwise the block is not drawn and `item_refs` is not read.

## CLI

| `overdue` | `--limit 10` `--list <slug>` | open items with `due_at` before now, the most recent first |
| `do` | `--list <slug>` `--limit N` | per list, quadrant A (stored or derived with the urgency window) in card order, up to the Do limit: the login's own settings, or with `--for <handle>` that person's (`rpc/urgency_settings`, db/012; household profiles only), else the defaults (agents: window 7 days, limit 5) |
| `restore-list` | `--list <slug>` | un-archives a list (people only: `--as maksym` or `anastasiia`) |

- **Lists:** `<list>` is a slug, or `OWNER/slug` when two owners use the same slug (slugs are unique per owner); with several matches household lists win, else exit 1 naming each `owner/slug`.
- **Who an item is for:** `--owner` (a person's handle, or `none`) sets `owner_id`; `--notify` takes people's handles into `details.notify`. Owner tags are never written: `maksym` or `anastasiia` in `--tags` set the owner, `shared` (or both names) sets none, and the tag is dropped (`ownerFromTags`). The owner must be a member of the list (else 22023, exit 1).
- **Common options:** `--env <file>` (KEY=value lines; `TASKSDB_*` variables from the environment fill gaps), `--as <handle>` (default `homeos-agent`; reads `TASKSDB_<HANDLE>_EMAIL` / `_PASSWORD`, with `AGENT` and `TELEGRAM` for the two agents), `--for <handle>` (`on_behalf_of`, a person), `--via <channel>` (`created_via` and `x-homeos-via`, default `script:tasks-cli`), `--run-id`, `--json`, `--dry-run` (reads, sends no write).
- **When:** `YYYY-MM-DD` (09:00) or `YYYY-MM-DD HH:mm` in Europe/Lisbon, or ISO with an offset.
- **Env:** `TASKSDB_URL`, `TASKSDB_ANON_KEY` (the publishable key), and the login pairs. The URL and key get the page's config checks (https or localhost, never a secret key); a failure is exit 2.
- **List status:** every write reads its list first; an archived list is exit 8 and nothing is sent. `overdue` and `do` skip archived lists.
- **Output:** one line per item, `<initial><num> · title · due · list`, or `--json`.
- **Exit codes** (`EXIT`): 0 ok, 1 error (including not allowed and a bad value, 22023 without "sensitive data"), 2 env missing, 3 conflict, 4 duplicate, 5 sensitive data, 6 unreachable, 7 auth failed, 8 list archived (or, for `restore-list`, not archived or not found), 9 a limit (54000, see Limits).
- It never prints an env value, a token or a password.

## Hosting

The same two files can be served by any static host over https; nothing in the app changes. Setup steps, headers and the verified free-plan facts: `docs/hosting.md`; sign-in on a hosted origin: `docs/auth.md`.

- **Allow-list:** `TasksDashboard.html` published as `index.html`, plus `config/tasksdashboard.config.js` at the same relative path, `privacy.html` (no script) and `request.html` (served at `/request`, one inline script). Nothing else: not `db/`, `cli/`, `test/`, `docs/`, `config/profiles.js`, `config/*.prefs.json` or the Markdown files. A `version.json` with the commit sha helps a version check.
- **CSP** (a response header, one policy for every path): `script-src 'self'` plus `'sha256-<base64>'` of the body of each inline `<script>` of `TasksDashboard.html` and `request.html` (line endings as LF), `connect-src` = the `supabaseUrl` from the config, `default-src 'none'`, `style-src 'unsafe-inline'` (the timeline writes `style` attributes), `img-src 'self' data:`, `base-uri 'none'`, `form-action 'none'`, `frame-ancestors 'none'`, `object-src 'none'`. A new inline script, external script or network host changes the hashes or the policy.
- The KPI styles are added as a `<style>` element by the UI script (allowed by `style-src 'unsafe-inline'`), and Download saves a `blob:` URL through `<a download>` (no navigation, no fetch): neither changes the CSP.
- The full header set, the cache rules and the household's Cloudflare Pages deploy: `docs/deployment/2-deploy.md`.
- Access requests (the public `/request` page, `db/015`, `cli/access.mjs`, the Cloudflare setup, seats, switch-off): `docs/access-requests.md`.
- Storage is per origin: a hosted copy has its own `td.auth`, `td.accounts`, `td.pkce`, `td.theme` and `td.rail`. Sign in once on each; signing out of one leaves the other signed in.
- Supabase needs no change for a password-only sign-in (CORS allows any origin). Google sign-in needs the hosted URL as Site URL and `<origin>/**` under Redirect URLs (the household's: `https://homeos-tasksboard.pages.dev/**`, `http://localhost:8787/**`), and the Google provider on.

## Limits

- Local (`file://`), or hosted: see `docs/deployment/` and, in HomeOS, `references/homeos/tasksdb/hosting-plan.md`. The household copy is on Cloudflare Pages behind Cloudflare Access. Supabase's free plan cannot serve the page as HTML.
- `file://` storage is shared by every local page in the same browser profile: they can read `td.auth` (a refresh token), `td.accounts` (email addresses) and the `td.auth` BroadcastChannel (new token pairs). Open only files you trust in that browser profile; sign out on a shared computer. A hosted copy's storage is readable only by its own origin.
- On the free plan a session never times out; Sign out (or revoking sessions in the dashboard) ends it.
- No trash view: a deleted item is recoverable only by admin SQL after the 8 s Undo.
- No password sign-up and no password reset in the app; new accounts come only through Google (when sign-ups are on, behind the sign-up hook). `file://` has no Google sign-in.
- No unblock in the app: "Decline and block" is undone by deleting one's own `invite_blocks` row (REST) or by admin SQL.
- **Limits** (`ops.settings`, `db/009`; admin SQL tunes them). Over one: 54000 in plain words, CLI exit 9.

  | Who | Limit |
  |---|---|
  | guests | 20 live lists (100 with archived), 1,000 live items they created (3,000 with deleted), 500 live tags, 10 live tag lists (50 with archived, `db/012`), `body_md` ≤ 10,000 characters, `details` ≤ 8 KB, 2,000 item writes a day, 120 item writes a minute |
  | household | 50 live lists each, 5,000 live items per list, 5,000 live tags, 30 live tag lists each (`db/012`), 1,000 item writes a minute (people and agents) |
  | tags | tags in archived tag lists still count toward the tag limits; Mine (`mine_tag_ids`) counts at most 50 tags |
  | everyone | 20 invitations a day, 50 open at once; an invitation expires after 30 days |
  | access requests | 20 a day from everyone, 30 pending at once (`access_requests_per_day`, `access_requests_open`, `db/015`); one open request per person |
  | sign-up hook | Google sign-ups refused at 200 human profiles or a 400 MB database ("TasksDashboard is full right now"); password sign-ups only with a one-shot `ops.signup_allowlist` row (15 minutes) |

- Guests never see the household categories (`tbd`, `decision`, `candidate`, `plan`, `wish`, `renewal`), household profiles, or another person's tags unless that person shares a tag list with them.
- **KPI:** an item counts in the list it is in now (events are readable through the item's current list), so a moved item's history follows it; the quadrant of the past is derived with today's urgency settings; history starts at the audit trigger (`db/002`), before it items show as they are now. Without `db/013` the history comes in REST pages, four at a time: about 0.6-0.7 s for each 4,000 events (measured 2026-10-28), so about 12,000 events fit in 2 s.
- Links in descriptions and sources are shown as text.
- No repeat, subtasks, effort, reminders delivery or `.ics` export in the app.
- The End field uses the browser's date-time control, so its format follows the system locale.
